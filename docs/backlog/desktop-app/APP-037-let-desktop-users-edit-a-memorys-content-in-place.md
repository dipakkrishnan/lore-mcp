## Problem

APP-011 let desktop users open a memory from the list, but there is still no
way to fix a mis-captured or stale one short of dropping to the CLI's `lore
memory edit`. The desktop app is meant to be a complete surface for owning
your library, not a read-only mirror of it.

## Proposed approach

- Add a save action to the memory sheet that calls `lore memory edit <id>
  <content> --json` (via `state.cjs::editMemory`) and re-renders the card on
  success.
- Give the CLI's `memory edit` a `--stdin` flag as the sole trigger for
  reading content from stdin, replacing the old `content == "-"` sentinel.
  The sentinel collided with a memory whose content is literally `-`: the
  desktop path always forwards content as a direct argument with no way to
  say "this is literal, not a stdin request," so that content could never be
  saved through the desktop app.

## Acceptance criteria

- [x] Desktop's memory sheet exposes an edit action that saves new content
      through the CLI and re-renders the memory
- [x] A memory whose content is literally `-` round-trips correctly through
      the desktop edit path
- [x] `lore memory edit` supports `--stdin` for the terminal-pipe case,
      decoupled from the positional `content` value
